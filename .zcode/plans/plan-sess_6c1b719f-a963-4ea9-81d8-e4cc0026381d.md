# 修复 AlphaBrief 生产环境（部署在 ~/.alphabrief），使其完整可用

## 诊断结论（已完成）
仓库本身全绿（1370 tests / ruff / mypy / acceptance 11/11），但**生产系统实际不可用**，共 6 个真实缺陷：

1. **AI 交易委员会完全死亡（根因）**：`run_scheduler.sh` 与仓库 `.env` 的 `OPENAI_API_KEY` 都是 13 字符占位符 `sk-te9...tB6e` → 所有模型调用 401 → 13 轮循环全部零票 `skipped_no_consensus`、零 plan、零 attempt。30 天观测实际什么都没产出。
2. **故障被静默掩盖**：零票被记成 `skipped_no_consensus`（看起来像正常的市场结论），仪表盘/导出 JSON 无法暴露模型调用失败。
3. **1,297,161 条告警垃圾**：冻结期间调度器每个 5s 轮询每条 task 都写一条 "open freeze detected" 告警（7/1→8/12），DB 膨胀、告警页不可用。
4. **ai_daily_cycle 任务超时过短（120s）**：预取数据（yahoo×3 + RSS×3）+ 12 次模型调用（单次上限 30s）很可能超过 120s → 连续 3 次超时自动冻结调度器。**key 修好后必然触发**。
5. **仪表盘 AI 页永远空白**：API 读自己的空 api-data DB（DuckDB 单写锁，已验证 read-only 也无法并发读调度器 DB）→ cycle_count 恒为 0。
6. **部署不可复现**：run_api.sh / run_scheduler.sh / daily_check.sh 只存在于 ~/.alphabrief，仓库无副本、文档未覆盖。

## 代码修复（仓库内，全部安全边界不动）
1. **provider_error 结局**：`TradingCommittee` 收集 `role_errors`；`DailyTradingCycle` 在"所有角色调用失败"时记录 `provider_error`（新 CycleOutcome 值）+ 首条错误摘要，照常落库并导出 → 故障可见。不动 RiskGate / 执行策略 / 风控语义。
2. **冻结告警去重**：`OperationsScheduler._run_task` 对每个冻结事件（`list_freezes(only_open=True)` 的 event_id）× 每个 task 只发一条告警，之后静默轮询。
3. **超时修正**：`build_default_tasks` 中 `ai_daily_cycle` timeout 120s → 900s。
4. **API 观测面**：`/api/v1/ai/{status,history,cycles/{id},attempts}` 在设置 `ALPHABRIEF_AI_OBSERVATION_DIR` 时改读调度器导出的 `ai_cycle_*.json`（调度器已按天导出完整记录，无需新增写入）；`POST /ai/run` 仍写 API 自有 DB。
5. **部署脚本入库**：新增 `scripts/deployment/{run_api.sh,run_scheduler.sh,daily_check.sh}`（占位符密钥 + 注释），修 daily_check.sh 路径不一致；更新 `docs/paper_broker_setup.md` 与 `docs/development_log.md`。
6. **.env**：写入真实 key（gitignored，不会入库）。
